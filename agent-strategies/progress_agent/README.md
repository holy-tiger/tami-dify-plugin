# 进度感知 Agent 策略

基于官方 Function Calling 实现的自定义插件。插件每轮向模型提供真实轮次、剩余预算、检查点标记和收尾标记；进展评估、调整方法、向用户补充提问等行为由 Chatflow Agent 节点的「指令」配置。

插件标识：`tami/progress_agent`；版本：`0.0.2`；策略：`progress_function_calling`；要求 Python 3.12、Dify >= 1.7.0，以及支持原生函数调用的模型。

## 安装与配置

1. 在 Dify 插件页通过本地文件上传 `.difypkg`。
2. 在 Chatflow 的 Agent 节点选择「进度感知 Function Calling」。
3. 设置模型、工具、指令、查询。
4. 配置四个预算参数。它们使用**支持变量/模板的文本输入**，可以填整数常量，也可以通过变量选择器插入会话变量或上游节点输出。
5. 将下方「推荐增加到 Agent 节点的指令」追加到业务指令中，并按任务需求调整。插件没有内置进展检查提示词；只有状态标记不会自动定义评估规则。

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `maximum_iterations` | `30` | 模型调用总上限，包含收尾；1–500。 |
| `progress_check_start` | `20` | 首次检查进展的轮次；1–最大轮数。 |
| `progress_check_interval` | `5` | 此后每隔多少轮检查；1–500。 |
| `final_response_rounds` | `1` | 尾部禁用工具的收尾窗口；1–最大轮数。 |

例如创建会话变量 `agent_max_iterations=30`、`agent_check_start=20`、`agent_check_interval=5`、`agent_final_rounds=1`，分别插入对应参数。模板引用通常形如 `{{#conversation.agent_max_iterations#}}`；以你的 Dify 版本的变量选择器生成的引用为准。插件收到的是 Chatflow 已解析的值，不自行执行表达式。

默认配置会在第 **20、25 轮**设置检查点标记，第 **1–29 轮**可执行工具，第 **30 轮**禁用工具。配置推荐指令后，模型会在检查点评估进展，在收尾阶段总结或提问。第 20 轮开始时，本轮之后还有 10 轮，包括本轮还有 10 轮可以执行工具。同一轮模型可以请求多个工具，策略会依次执行；轮数不等于工具数量，也不是完成百分比。

小预算示例：`5 / 2 / 2 / 1` 表示上限 5 轮，在第 2、4 轮检查，第 5 轮收尾。缩小上限时要同步调整首次检查轮次。上限为 1 时只能回答或提问，首次检查也应设为 1。检查点落入收尾窗口时，以收尾为准。

所有参数必须解析为整数：空值、未解析的变量引用、布尔值、小数、超出 1–500、检查起点或收尾窗口超过总预算，都会在首次调用模型前报错。通过 API 直接传入整数数值（包括 `30.0`）可接受；文本输入使用 `30` 等整数形式。API 调用省略检查起点时，小预算会自动缩短默认起点；显式传入的值严格校验。

## 每轮提供给模型的状态

插件在原有 Agent 指令后追加当前轮次的状态块，例如第 20 轮：

```xml
<iteration_budget>{"current_iteration": 20, "maximum_iterations": 30, "remaining_iterations_after_current": 10, "remaining_tool_rounds_including_current": 10, "final_response_rounds": 1, "is_checkpoint": true, "is_finalization": false}</iteration_budget>
```

| 字段 | 含义 |
| --- | --- |
| `current_iteration` | 当前模型调用轮次，从 1 开始。 |
| `maximum_iterations` | 本次执行的模型调用上限，包含收尾。 |
| `remaining_iterations_after_current` | 本轮结束后剩余的模型调用轮数。 |
| `remaining_tool_rounds_including_current` | 包含本轮在内，还允许执行工具的轮数。 |
| `final_response_rounds` | 配置的尾部无工具收尾窗口大小。 |
| `is_checkpoint` | 本轮是否是进展检查点；如何检查由 Agent 指令决定。 |
| `is_finalization` | 本轮是否进入禁止调用工具的收尾阶段。 |

插件只追加状态数据，不附加“改变方法”“向用户提问”等行为指令。预算计算模块负责参数校验和状态计算，模型调用层负责将状态送入当轮上下文。状态每轮更新，不会把旧状态累计到历史中。

## 推荐增加到 Agent 节点的指令

把下面内容追加到 Agent 节点现有业务指令中，保留你自己的任务目标、工具使用规则和输出要求。此段指令由你在 Dify 中维护，调整后无需重新打包插件；也可以通过节点指令的变量引用功能引入统一维护的规则。

```text
【迭代预算与进度管理】

运行时会在系统上下文中提供 <iteration_budget> JSON 状态块。
使用该状态中的真实轮次和剩余预算规划任务，不要自行估算已执行的轮数。
一次迭代表示一次模型调用，一轮可能请求多个工具；轮数不代表任务完成百分比。

一、每轮遵循
- 根据已验证的工具结果判断进展，不编造结果，不将计划执行的动作描述为已完成。
- 任务完成后及时给出最终答案，不需要用完迭代预算。
- 任何轮次发现缺少只有用户才能提供的必要信息时，说明已完成事项，提出具体问题并结束本次执行；无需等到检查点。
- 能通过已有工具合理获取的信息，优先自行获取，不把一般探索困难直接转为用户问题。

二、当 is_checkpoint 为 true 时
- 评估已完成事项、剩余工作、最近几轮的实际进展和阻碍。
- 结合 remaining_tool_rounds_including_current 判断剩余工具轮次是否足以推进或完成任务。
- 若近期尝试没有带来有用信息，调整方法，避免无新证据的重复尝试。
- 若缺少用户信息，提出具体澄清问题并结束本次执行。
- 若仍可取得实际进展，选择明确、必要的下一步继续执行。
- 若预算不足以完成任务，优先处理最有价值的剩余步骤，并为收尾保留清晰的结果摘要；若已无有效推进路径，直接说明部分结果和阻碍。

三、当 is_finalization 为 true 时
- 不再请求工具，也不依赖后续工具调用或下一轮执行来完成当前回答。
- 根据已有证据给出最终答案；若任务未完成，说明已完成事项、剩余工作和具体阻碍。
- 仅在确实需要用户信息时提问；若只是需要更多执行预算，应明确说明需要继续执行，不要虚构缺失信息。
- 不声称尚未验证的任务已经完成。

使用用户的语言回答，保持简洁。只给出有用的进展或结果摘要，无需展示完整内部推理，也不必每轮播报状态字段。
```

这段指令是可修改的推荐策略。插件只保证真实计数、总轮数上限、检查点标记和收尾阶段禁用工具；是否识别阻碍、是否提问及摘要内容依赖你配置的指令和模型表现。

## 执行边界

- 每次执行从第 1 轮重新计数，每轮仅注入当前预算，不累计旧预算提示。
- 检查点通过 `is_checkpoint=true` 表示，进展判断规则来自 Agent 节点指令。模型可在任何轮次提前完成或向用户提问。
- 进入收尾窗口后不再向模型提供工具；模型仍返回的工具请求也不会执行。不会在总预算之外再追加总结调用。
- `final_response_rounds=2` 表示提前进入禁止工具的窗口，首个最终回答即结束，不会强行追加第二次总结。通常使用 `1`。
- 空白响应或收尾阶段的违规工具请求会产生明确兜底提示，避免静默结束。
- 按推荐指令进行的进展评估在当前模型调用内完成，不额外调用评审模型。是否受阻依赖模型判断，插件不保证能识别所有停滞。轮数上限不代表 token、工具耗时或总耗时上限；平台超时仍然适用。

## 向用户提问后继续

提出问题会**结束本次 Agent 执行**。用户下一条消息重新触发 Chatflow 和新的迭代预算，插件不实现当前工作流原地挂起、等待回复及恢复。

建议启用 Agent 节点历史消息，并按业务需要通过会话变量保存进度摘要，再在指令中引用。不要假定下一次执行会自动获得所有工具结果或续接旧轮次。

保留官方历史消息、当前轮图片/文件、检索上下文、工具允许列表等输入。`allowed_tools` 留空时允许全部已选择的工具；工具生成的文件会继续转发。

最终 JSON 包含费用信息 `execution_metadata` 和迭代信息 `iteration_metadata`：使用轮数、最大轮数、剩余轮数、到达的检查点、是否进入收尾、被阻止的工具请求数量及 `stop_reason`。后者可能是 `model_response`、`finalization_response`、`tool_call_blocked` 或 `empty_response`，表示执行结束方式，**不表示已证明任务完成**。需要时使用下游代码节点读取 Agent 的 JSON 输出，具体变量选择以 Dify 版本为准。

## 开发、测试与打包

在插件目录运行：

```bash
uv sync --frozen --all-groups
uv run --frozen python -m pytest -q
uv run --frozen ruff check .
uv run --frozen ruff format --check .
```

远程调试：复制 `.env.example` 为 `.env`，填写 Dify 提供的调试地址、端口和密钥，运行 `uv run --frozen python main.py`。示例未包含有效密钥。插件本地执行超时配置为 900 秒，实际部署可能施加更短的超时。

在仓库根目录使用官方 Dify Plugin CLI 打包：

```bash
dify plugin package agent-strategies/progress_agent --output_path /tmp/progress_agent-0.0.2.difypkg
```

插件包可以独立加载，不依赖旁边的 `cot_agent` 目录。本地测试模拟模型和工具响应并验证 SDK 注册；真实模型、Chatflow 界面和用户下一轮续接仍需在实际 Dify 中联调。

本插件的 Function Calling 引擎和工具辅助代码源自官方 `langgenius/dify-plugins` 的 `cot_agent`，遵循 Apache-2.0 许可证，详见 [LICENSE](LICENSE)。这是 Tami 自定义插件，独立维护，不属于官方发布版本。
